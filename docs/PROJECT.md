更新：2026-10-19。项目名称：集屿 / Jiyu（用户已确认）。

## 用户目标

把微信等渠道零散收到的文件，转为一个链接集中收集，按任务与提交人整理。部署到自己的 VPS；存储可选择本地或网盘；通过批量工具和悬浮 AI 减少重复劳动。

当前用户已确认的方向：先做界面确定风格，简约高级，使用 frontend-design 技能辅助；最新要求参考 Claude 的感觉，采用暖纸色、炭灰文字、陶土点缀与衬线标题。框架采用推荐方案搭建前端；后端选型作为建议，尚未开始实现。

## 控制目录增长

1. 不创建 `v2/`、`final/`、`backup/` 等源码副本。历史依靠 Git，当前界面作为首个版本纳入管理；推送按用户授权执行。
2. 不提前搭空的 monorepo。真正开始后端时再增加 `server/`，复用 TypeScript 类型，先保持单仓库。
3. `node_modules/`、`dist/`、`.cache/`、`.artifacts/` 是可再生内容。截图与临时样本仅进 `.artifacts/`；npm 缓存可随时清理。
4. 开发依赖仅在本地/构建阶段使用。部署只打包应用构建结果与正式服务依赖，不把 npm 缓存和原型截图带上 VPS。
5. 正式版数据放独立挂载，例如 `/var/lib/jiyu/`；与应用发布目录分开。数据库、上传和备份不进 Git 或 Docker 镜像。
6. 日志轮转、临时上传定期清理、单任务/全局配额、回收站保留期、备份保留上限需要在 P1/P2 实现并验证。
7. 增加依赖前说明用途。简单状态用 React；简单弹窗用原生 dialog；本阶段无 UI 大组件库、状态库或路由库。

## 进入后端前要确认

- 风格、信息密度与任务字段是否适合实际使用。
- VPS 系统、配置、域名与 HTTPS 入口。
- 真实需求中的文件大小、单次提交数量、并发规模和保留时长。
- 最常用的网盘具体是哪家，以及是否有可用的官方授权/API。
- 上传人是否匿名，是否需要密码、名单与提交回执。

## Git 管理

- 仓库：[1Beyond1/jiyu](https://github.com/1Beyond1/jiyu)，公开仓库，默认分支 `main`，本地远端名为 `origin`。
- 作者与维护者：`1Beyond1`。本仓库的提交邮箱为 GitHub 隐私邮箱 `142073741+1Beyond1@users.noreply.github.com`，不把个人邮箱公开到新提交中；不修改其他项目的 Git 身份。
- 初始版本：`v0.1.0`，对应可交互的 P0 界面原型。此标签不代表真实文件服务已可投产。
- `.gitattributes` 统一文本为 LF；`.editorconfig` 统一编辑器格式；保留唯一 `package-lock.json`。
- GitHub Actions 使用 Node.js 24，执行 `npm ci` 与 `npm run build`。在 `main` 推送、PR 和手动触发时运行；官方 action 固定提交号，工作流只授予读取仓库权限。
- 全部路径的默认维护者由 `.github/CODEOWNERS` 指向 `@1Beyond1`。PR 模板记录改动目的与验证结果。
- GitHub 合并方式采用 squash，合并后自动删除功能分支。个人项目暂不要求其他人审批自己的 PR。
- 不强制推送或删除 `main`，不提交可再生内容、用户文件、凭证或本地配置。不要创建源码副本充当备份。

后续开发采用以下流程：

```sh
git switch main
git pull --ff-only
git switch -c feat/short-description
# 开发并检查差异
npm run build
git add <本次改动的具体文件>
git diff --cached
git commit -m "feat: describe the change"
git push -u origin feat/short-description
# 在 GitHub 提交 PR，检查通过后 squash 合并
```

提交信息使用 `feat:`、`fix:`、`docs:`、`chore:` 等简短前缀。一个提交解决一个清楚的问题；初始界面基线作为一个完整提交保存。
